# prisma/sql — ручные SQL-скрипты и разбор дрейфа миграций

## Дрейф миграций (важно)

Единственная миграция в `prisma/migrations` — `20260413050614_init` — не
содержит половины актуальной схемы: `PaymentSplit`, `CashIncome`,
`ProjectCache`, `UnitProjectCategory`, полей `paymentMethod`, `adeskSafeId`,
`tgChatId/tgMessageId/tgThreadId` и др. Значит прод обновляли через
`prisma db push` мимо истории миграций.

Последствия: `prisma migrate deploy` на чистом окружении (новый сервер,
восстановление из бэкапа) создаст БД без этих таблиц, и приложение упадёт на
первом же запросе. `prisma migrate dev` увидит drift и предложит reset (потерю
данных).

### `full-schema-baseline.sql`

Полный SQL актуальной схемы (сгенерирован
`prisma migrate diff --from-empty --to-schema ./prisma/schema.prisma --script`).
Включает и новый уникальный индекс `Payment_adeskConfirmedTransactionId_key`.

Это эталон текущей схемы — используйте его как baseline при восстановлении
истории миграций.

### Как выровнять историю (на проде, где таблицы уже есть)

Прод уже содержит все таблицы (их накатил `db push`), трогать данные не нужно —
нужно лишь привести в порядок _историю_ миграций, чтобы `migrate deploy` работал
дальше. Порядок (сверяйтесь с доками Prisma для вашей версии):

1. Снимите бэкап БД.
2. Сначала выполните `dedup-adesk-tx.sql` (см. ниже) — иначе уникальный
   индекс не создастся из-за существующих дублей.
3. Создайте baseline-миграцию из этого файла и отметьте её применённой:
   `prisma migrate resolve --applied <имя_миграции>`.
4. Убедитесь, что `prisma migrate status` показывает согласованное состояние.
5. Впредь применяйте изменения только через `migrate`, не через `db push`.

## `dedup-adesk-tx.sql`

Разовая чистка дублей привязок перед включением
`@unique` на `Payment.adeskConfirmedTransactionId`. Подробности — в шапке файла.
Запускать ДО применения схемы с констрейнтом.
